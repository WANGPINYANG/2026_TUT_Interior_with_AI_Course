## 發現：5 項

### 1. 極大值與無限大造成程式當掉【高】

- 壞值：`--length 1e308`、`--length inf`、或 `--length 1e200 --width 1e200 --height 1e200`
- 實際結果：**吐出 Python traceback**

  ```
  OverflowError: cannot convert float infinity to integer
  ```

- 期望結果：比照其他參數乾淨拒絕，而不是把 traceback 丟給使用者
- 根因：`positive()` 的檢查是

  ```python
  number = float(value)
  if number <= 0:
      raise argparse.ArgumentTypeError("must be greater than 0")
  ```

  **`inf > 0` 為真，所以無限大穿得過去**；到了 `math.ceil(inf)` 才爆炸。
  有限的極大值（1e308）在相乘後也會變成 `inf`，走同一條路。
- 截圖：`screenshots/l001-溢位當掉.png`
- 已修：否

**這跟我自己 9/19 被抓到的是同一個洞**：驗證器只檢查範圍（大於 0），沒檢查有限性。
我後來的修法是加一個「出口關卡」——回傳前掃描結果，任何非有限數一律轉成錯誤，
這樣不管哪個參數、哪種組合造成溢位都會被攔住，不用逐一猜。

### 2. 輸出的 JSON 不是合法 JSON【高】

- 壞值：`--unit-price 1e308`
- 實際結果：

  ```json
  "unit_price": 1e+308,
  "material_subtotal": Infinity
  ```

- 已驗證的後果：

  ```
  JavaScript JSON.parse  → ★ 失敗：Unexpected token 'I'
  Python json.loads      → 成功（但 Python 預設寬鬆，不代表合法）
  Python 嚴格模式        → ★ 失敗
  ```

- 期望結果：JSON 規格沒有 `Infinity` 這個字面值。
  應該在輸出前就擋掉，或改成 `null` 並附註說明
- 截圖：`screenshots/l002-非法JSON.png`
- 已修：否

這條的實務影響比看起來大：這支工具的輸出是設計給程式吃的，
**只要下游用標準 JSON 解析器就會直接炸掉**，而且錯誤訊息會指向解析端，
很難追回到估算工具這裡。

### 3. 極小值造成除以零當掉【中】

- 壞值：`--tile-length-cm 1e-300 --tile-width-cm 1e-300`
- 實際結果：`ZeroDivisionError: float division by zero`（traceback）
- 期望結果：乾淨拒絕
- 根因：`positive` 只擋 `<= 0`，1e-300 是正數所以通過；
  但兩個 1e-300 相乘得到 1e-600，在 float 下直接變成 0.0，接著當除數
- 截圖：`screenshots/l003-除零當掉.png`
- 已修：否

**單一參數合法、相乘之後才變成 0** ——這跟第 1 項是鏡像關係（一個往上溢位、一個往下溢位）。

### 4. 無限大參數得到「0」這種看起來合理的錯誤答案【中】

- 壞值：`--coverage inf`（油漆）、`--roll-width inf`（壁紙）
- 實際結果：

  ```
  --coverage inf   → "containers": 0     （需要 0 桶油漆）
  --roll-width inf → "rolls": 0          （需要 0 捲壁紙）
  ```

- 期望結果：拒絕無限大輸入
- 截圖：`screenshots/l004-零桶油漆.png`
- 已修：否

**這比當掉更危險。**當掉使用者知道要找人，但「需要 0 桶油漆」是一個格式完整、
看起來像正常答案的輸出，照著下單就是沒買。

### 5. 極小參數得到三百多位數的答案【中】

- 壞值：`--coverage 1e-300`、`--roll-width 1e-300`
- 實際結果：`containers` / `rolls` 是一個 300 多位數的整數
- 期望結果：加上合理範圍的上限檢查
- 截圖：`screenshots/l005-天文數字.png`
- 已修：否

這條本身很明顯（沒人會看不出來），但它代表參數缺乏合理範圍檢查——
跟第 4 項是同一個根因的兩端。


### 6. 正常合理的輸入會多買一箱（浮點進位）【高】

- 壞值：**完全正常的輸入**，沒有任何極端值

  ```
  paint --length 5 --width 5 --height 2.5 --coverage 1 --coats 1 --container-liters 5 --waste-percent 10
  tile  --length 10 --width 10 --tile-length-cm 100 --tile-width-cm 100 --tiles-per-box 10 --waste-percent 10
  ```

- 實際結果（我獨立重跑驗證）：

  | | 實際輸出 | 手算 |
  |---|---|---|
  | paint | `required_liters_with_waste: 55.0`、`containers: **12**` | 55 L ÷ 5 L＝**11 桶** |
  | tile | `required_tiles_with_waste: **111**`、`boxes: **12**` | 100 × 1.1＝**110 片、11 箱** |

- 根因（已驗證）：二進位浮點的微小超額直接進了 `ceil()`

  ```
  100 × 1.1 = 110.00000000000001  → ceil = 111
  50 × 1.1 = 55.00000000000001    → ÷5 = 11.000000000000002 → ceil = 12
  ```

- 截圖：`screenshots/l006-浮點多買.png`
- 已修：否

**這是整份報告裡最該先修的一條**，理由有三個：

1. **不需要任何極端輸入。**10×10 公尺的房間、100×100 公分的磚、10% 損耗——
   都是現場天天會遇到的數字。
2. **paint 的輸出自相矛盾。**畫面寫 `55.0` 公升、桶是 5 公升，任何人都會算出 11 桶，
   它卻說 12 桶。真值是 `55.00000000000001`，**顯示時被四捨五入成 55.0，
   bug 的證據被顯示邏輯藏起來了**。
3. **加 `isfinite()` 完全修不好這一條。**它跟前五項是不同的根因。

建議的修法方向：進位前先消掉浮點雜訊，例如 `math.ceil(round(x, 9))`，
或改用 `decimal.Decimal` 做金額與數量的計算。不要隨便減一個固定的 epsilon。

### 建議的修復優先序

0. **第 6 項（浮點多買一箱）**——唯一不需要極端輸入就會發生的，而且輸出自相矛盾。
   它跟其他項是不同根因，加 isfinite() 修不好。
1. **第 1、3 項（當掉）**——加一個統一的有限性檢查即可同時解決。
   建議在 `positive` / `nonnegative` 裡加 `math.isfinite(number)`，
   這樣所有用到這兩個驗證器的參數一次全部修好。
2. **第 2 項（非法 JSON）**——輸出前掃一次結果，非有限數就轉成錯誤或 `null`。
3. **第 4、5 項**——加參數的合理範圍上限（例如 coverage 不會超過 100 m²/L）。

### 一句話的觀察

她的參數驗證做在正確的位置（argparse 層），比我第一版好；
問題全部出在**驗證器檢查了範圍但沒檢查有限性**——`inf > 0` 為真，所以無限大是個「正數」。

這跟我 9/19 被第三方稽核抓到的完全是同一個洞。
我的修法是加「出口關卡」：回傳前掃結果，非有限數一律轉錯誤。
這招的好處是不用逐一猜哪個參數會溢位，新增功能也自動適用。
